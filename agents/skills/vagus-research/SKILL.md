# vagus research を操る

vagus の常駐コンテナで走る `vagus research` を、ホストの管理コマンド `vagus` から操る。
本体（planner、並列の作業役、integrator のラウンドと最終の成果物）は vagus が持つ。
作業役は、事実を確かめる investigate、設計案を起こす propose、案を崩しにいく critique の 3 種類で、planner が課題ごとに選ぶ。
設計の問いは、推す案が critique を通るまで終わらない。
この skill の役割は、問いを固めて渡すこと、進み具合と報告書を読んで伝えることである。

## コマンド

vagus のリポジトリの外から打つと、管理コマンドがリポジトリを見つけられない。
どのコマンドにも `--repo "${VAGUSCTL_REPO:-$HOME/src/github.com/bw-company/vagus}"` を付ける（下では `--repo …` と略す）。

```bash
vagus --repo … research start <名前> <<'EOF'   # 問いを標準入力で渡し、切り離して始める
...
EOF
vagus --repo … research status                 # 一覧（走行中か、完了したラウンド数、報告書の有無）
vagus --repo … research status <名前>          # 1 件の状態とラウンドごとの要約
vagus --repo … research report <名前>          # 報告書
vagus --repo … research resume <名前>          # 止まった調査を続きのラウンドから再開する
```

作業ディレクトリはコンテナの `/data/research/<名前>` にある。
ホストのファイルとしては見えないので、中身は上のコマンドの出力で読む。

## 始める

1. **問いを固める。**
   planner は問いから外れる課題を捨てるので、範囲が曖昧なまま渡すと調査も散らばる。
   依頼から次の項目を埋めた `question.md` の草案を作る。
   - 問い：答えてほしいこと、または設計してほしいものを 1〜3 文で書く
   - 答えに含めてほしいもの：比較表、推奨、根拠の一覧、設計文書など
   - 範囲：調べる対象と、調べなくてよい対象
   - 前提と制約：時期、地域、情報源の指定（「公式ドキュメントだけ」など）、手元の事情
   - 設計の問いでは、要求（満たすべきこと）と制約、対象のリポジトリ（コンテナの `/data/code` の下の `<org>/<repo>`）
   - 成果物の言語（既定は問いと同じ言語）

   要求はワクさんの言葉から取る。skill が補った要求は、補ったと分かる形で見せて確かめる。
   作業役は問いに書かれた要求を上限として扱うので、補った要求がそのまま設計を縛る。

   埋まらない項目のうち範囲を大きく変えるものだけを、ワクさんに会話で確かめる。
   埋められない細部は推測で足さずに、草案から外す。
2. **名前を決める。**
   英小文字、数字、ハイフンで、題材がわかる名前にする（例: `auth-survey`）。
   `research status` の一覧と重ならないことを確かめる。
3. **始める前に確認を取る。**
   草案と名前を見せ、始めてよいかを聞く。
   8 時間ほど走り、課題の本数は planner が問いの分解で決める（上限は無く、同時に走るのは既定で 5 本まで）。
   vagus の窓口と実装セッションと利用上限を分け合う。
   確認なしに始めない。
4. `research start <名前>` に草案を標準入力で渡す。
5. 始めたことと、進み具合の見方（この skill に「進み具合は？」と聞けばよい）を伝える。

## 進み具合と報告書

- **進み具合**：`research status <名前>` の出力から、走行中か、何ラウンド終えたか、直近のラウンドの進展と未解決の数、引用の照合の結果（照合 / 不一致 / 照合不能）、費用を 2〜3 行で伝える。
  不一致が多ければ、作業役の引用が出典に無い、つまり誤りが混ざっている信号なので、そのことも伝える。
  名前がわからなければ `research status` の一覧から選ぶ。
- **成果物**：`research report <名前>` の出力をスクラッチパッドのファイルに保存して読み、結論（設計なら推す案と、崩されずに残った理由）と未解決の点を短く伝える。
  全文を会話に貼らない。
  ワクさんが手元に置きたいと言ったら、指定された場所に書き出す。
- **再開**：止まった理由が時間切れや失敗で、続きを回したいときに `research resume <名前>` を使う。
  始めるときと同じく、再開する前に確認を取る。

## 失敗したとき

| 出力 | 原因と伝えること |
| -- | -- |
| `未知のコマンド research` の後に `vagus — Docker 上で動く vagus を運用する` | ホストの管理コマンドが古い。`vagus update` で差し替える |
| `未知のコマンド research` の後に `usage: vagus [command]` | コンテナのイメージが古い。`vagus build` と `vagus restart` が要る |
| `research には ports.claude = "real" と ports.agent = "real" が要る` | `vagus.toml` の `[ports]` の設定が足りない |
| `この調査はもう走っている` | 二重起動を断った。`research status <名前>` で進み具合を見る |
| `問いはもう書かれている` | 同じ名前の調査がある。別の名前で始めるか、`resume` で続ける |
| `報告書はまだ無い` | 調査が止まると書かれる。止まっているのに無ければ、完了したラウンドが 0 で終わっている |

`vagus build` と `vagus restart` は自分で打たない。
restart は常駐コンテナを止めるので、走っている実装セッションと調査が一緒に止まる。
打つかどうかはワクさんが決める。

## しないこと

- 作業ディレクトリを消さない。`vagus shell` で入って中身を書き換えない（`state.md` を直したいと言われたときは、手順を伝えるだけにする）
- 調査を止めない。止めたいと言われたら、`vagus shell` で入って `run.pid` の pid を kill する手順を伝える
