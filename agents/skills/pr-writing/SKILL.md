# Pull Request 執筆規範

Pull Request のタイトルと本文を書く、または更新するときは、以下に従う。
判断の基準は、diff を読む前に結論の見当がつき、読んだ後に疑問が残らず、一年後に読んでも判断の根拠が分かる状態にすることである。

## 書く前に確認すること

- リポジトリに PR テンプレート (`.github/pull_request_template.md` など) があれば、その見出しと項目に沿う。以下の規範はテンプレートの中身の書き方に適用する。
- 既存の PR を 3 件読み、タイトルの形式 (Conventional Commits の有無)、本文の言語、見出しの付け方を確認して揃える。
- 「なぜこの方法か」は diff から導けない。ユーザーから意図が与えられていなければ推測で埋めず、その旨を一行で書いて意図の記入を求める。

## タイトル

- マージ後に何が変わるかを一文で書き、結果を述語で言い切る。作業の名前 (「〜の修正」「〜の更新」) で終えない。
  - 悪い例: `ログイン処理の修正`
  - 良い例: `期限切れのセッションでログイン画面に戻す`
- 60 字 (英語なら 72 文字) 以内に収める。
- リポジトリが Conventional Commits を使っていれば接頭辞を付け、使っていなければ付けない。
- チケット番号は末尾か本文に置く。先頭に置かない。
- 「リファクタ」「整理」「更新」「修正」「対応」「Refactor」「Cleanup」「Update」「Fix bug」「Misc」だけのタイトルにしない。

## 本文の構成

テンプレートがなければ、次の見出しを使う。該当する内容がない見出しは、見出しごと削除する。

```markdown
## Why

## What

## 確認項目
```

- **Why**: なぜ今この変更が必要か。冒頭は「背景 → 問題 → この PR での解決」の順で書く。この方法を選んだ理由と、検討して採らなかった案があればその理由も書く。
- **What**: 変更の要点と、レビューで重点的に見てほしい箇所とその理由。diff を読めば分かる情報は書かない。
- **確認項目**: 何をどう検証したか。自動テストや手元で確認済みのものはチェックを入れる。「動作確認済み」だけでは書いたことにならない。

## 本文の分量

- 見出し、空行、末尾の Claude Code の attribution とセッション URL を除いて、10 行以内を上限とする。上限は目標ではない。3 行で足りるなら、それ以上は書かない。
- 変更したファイル、追加した関数、修正した行の列挙は書かない。diff を見れば分かる。
- issue や設計文書へのリンクは補足として貼る。リンク先を読まないと本文の意味が通らない書き方をしない。
- 見た目に関わる変更は、before と after の画像を添える。文章で描写しない。画像は `gh pr create` / `gh pr edit` の `--attach` で添付できる (gh 2.100 以降)。

```bash
gh pr edit 123 --attach './before.png#変更前の一覧画面' --attach './after.png#変更後の一覧画面'
```

## 本文の文体

- 常体 (だ・である調) で書く。「〜いたしました」「ご確認のほどよろしくお願いいたします」のような敬語と定型の挨拶は書かない。
- 一文ごとに改行する。
- 箇条書きの各項目は一行に収め、体言止めか短い述語で終える。
- テンプレートの項目に書くことがなければ、「N/A」「特になし」と書かずに項目ごと削除する。

## 使わない表現

次の表現は情報を増やさない。

- **断定を避ける言い回し**: `〜と考えられます` `〜が期待されます` `〜かと思います`。根拠があれば言い切り、不確実なら何が不確実かを具体的に書く。
- **中身のない形容**: `適切に` `包括的に` `堅牢な` `重要な`。何をどうしたかに置き換える。
- **予告と総括**: `本 PR では〜を行います` `以上が変更内容です` `まとめると`。
- **接続語の連続**: `また` `さらに` `加えて` で行を始めることを繰り返さない。
- **根拠のない影響範囲の記述**: `既存機能への影響はありません`。影響がないと判断した根拠 (テスト、呼び出し元の確認) を書くか、その文を消す。

このうち `〜と考えられます` などの定型句、`特になし` と `N/A` の行、タイトルの長さ、本文の行数、タイトル先頭のチケット番号は、textlint plugin の PR hook が `gh pr create` / `gh pr edit` の実行前に確認する。

## 更新するとき

- レビュー指摘への対応コミットには、どの指摘への対応かをコミットメッセージに書く。`address comments` のようにまとめて 1 コミットにしない。
- 議論の結果で方針が変わったら本文を更新する。コメントスレッドを読まないと真意が分からない状態で放置しない。

## 書き終えた後の点検

1. 本文の各行について、その情報は diff を見れば分かるか。分かるなら消す。
2. タイトルだけで、マージ後に何が変わるかが分かるか。
3. レビュアーがどこから読めばよいか、本文に示されているか。
4. 一年後に `git blame` からこの PR にたどり着いた人が、当時の文脈なしに判断の根拠を理解できるか。「例の障害」「先日の相談」のような相対的な参照は、具体的な名前や日付に置き換える。
