# Refactoring investigation

The reader will decide whether and how to refactor. Evidence about the current code matters more than advice.

```markdown
# <what should change, in one line>
<summary: the main structural problem, its cost, and the recommended direction, in one paragraph>

## Current structure
<modules, dependencies and data flow in scope, with absolute paths; a diagram in text or a table if it helps>

## Problems
<each problem with its evidence (code quoted with path and line), what it costs today, and how widespread it is>

## Plan
<ordered steps, each independently shippable, with what it changes, its risk and how to verify it; only a plan that survived critique>

## Alternatives considered
<other directions and why they lost>

## Risks and open questions
```
